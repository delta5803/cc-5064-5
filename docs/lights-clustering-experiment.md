# 灯光分簇实验 · 固定深度切分 vs 随可见深度自适应

本文是**空间划分讨论**的结论沉淀，配套一个可运行原型与可复算数据。目标不是给出一句
“自适应更好/更差”，而是把「近处密灯 + 远处空区」这类真实夜市负载做进仓库，用**光照误差**与
**列表量 / 查询成本**两组可复现的证据说清楚两种方案各自的取舍边界。

> 数字来源：`npm run experiment` → `artifacts/cluster-experiment.json` + `.md`；
> 正确性：`npm run verify`；图形入口：`npm start` 后浏览器对照面板。
> 三者都跑在同一份 `src/core` 内核上。

---

## 1. 讨论的问题与两种方案

分簇前向渲染里，屏幕被切成「屏幕瓦片 × 深度片」的簇，每簇维护一份灯索引列表。**深度方向怎么切**
直接决定每簇要循环多少盏灯、索引表多大、以及一个簇会不会超出容量。

| 方案 | 边界来源 | 直观预期 |
| --- | --- | --- |
| **固定切分**（fixed） | 指数等距：`boundary(k)=near·(far/near)^(k/K)`，全程均匀占用深度片 | 实现简单、与相机无关、每片深度跨度已知；近处片极薄、远处片极厚 |
| **随可见深度自适应**（adaptive） | 采样当前相机可见表面深度，按**等质量分位**放置边界，分辨率跟着几何走 | 把深度片预算花在“真的有表面”的深度；空区合并成少数大片 |

两者**接入同一个着色器**：分片索引不再写死指数公式，而是读一张 `uBoundaries[41]` 边界表
（`src/app/shaders.js`），CPU 内核 `sliceForViewDepth()` 与 GLSL `sliceForViewDepth()` 都在这张表上
二分查找。固定方案的边界表就是指数值，自适应方案是分位数值——**只换表，不换管线**。

### 为什么“先逆投影再查表”

硬件深度 `gl_FragCoord.z` 是非线性的，绝不能直接乘片数。两种方案都先逆透视恢复线性视深
`d = -zView`，再在边界表上定位片号。`verify.mjs` 里有一条硬检查：`sliceForViewDepth` 的表查找
与「线性扫描边界找到最后一个 `boundary<=d`」逐点一致（2000 个对数采样点，0 失配）。

## 2. 实验设置（仓库内可运行）

`src/core/experiment.js` 构造两种对抗性灯群，均 96 盏，都走同一个分配内核 + 同一 CPU 着色参考：

- **均匀灯群**（`buildUniformLights`）：灯沿街道在整段深度上均匀铺开，每簇占用的深度接近平均。
- **近面灯团**（`buildNearKnotLights`）：约 75% 的灯挤在相机前 12.5–18m 的一小团（近面密灯），
  其余稀疏散布到远处（远处空区）。

簇网格 320×180、瓦片 20px、24 个深度片；渲染 320×180 做逐像素参考对比。
场景含「均匀 / 近面灯团 / 紧预算 C=8 / 侧向环绕」共 5 个场景 × 2 分区。

**两条不可违反的规则**（由代码强制，不是口头承诺）：

1. **不允许靠漏灯降负载**：每帧渲染都拿「全灯参考」逐像素比对，并统计覆盖缺失。任何一次
   `coverageMissCount > 0` 都会让 `runOne()` / `comparePartitions()` 抛错、让 `npm run experiment`
   非零退出。所以表里每一行都是 0 漏光运行。
2. **不允许伪报**：所有 PSNR / 列表量 / 索引槽 / 加速比都来自 `renderImage` 与分配内核的真实输出，
   可用 `npm run experiment` 原样复算。

## 3. 结果：光照误差 + 列表量 + 查询成本

完整表见 `artifacts/cluster-experiment.md`。摘录关键行（96 灯，24 片）：

| 场景 | 分区 | PSNR | 漏光 | 每像素均值灯数 | 索引槽 | 实际显存 |
| --- | --- | --- | --- | --- | --- | --- |
| 均匀灯群 | 固定 | ∞ | 0 | 23.9 | 14046 | 108.9 KiB |
| 均匀灯群 | 自适应 | ∞ | 0 | 27.9 | 9639 | 91.7 KiB |
| 近面灯团 | 固定 | ∞ | 0 | 37.9 | 88732 | 400.6 KiB |
| 近面灯团 | 自适应 | ∞ | 0 | 33.8 | 24318 | 149.0 KiB |
| 近面灯团 · 紧预算 C=8 | 固定 | ∞ | 0 | 27.2 | 134892 | 580.9 KiB |
| 近面灯团 · 紧预算 C=8 | 自适应 | ∞ | 0 | 21.8 | 47799 | 240.7 KiB |

**光照误差**：两种方案对齐全灯参考都是 **PSNR=∞、最大差 0、差异像素 0、漏光 0**。
也就是说，在这里“两种深度切法”都**没有**牺牲光照正确性——差别全部落在列表量与查询量上。

**结论 1：索引量主要由“近面密灯 + 远处空区”的深度分布决定，不是切法本身。**
近面灯团场景固定切分需要 88732 槽，自适应只要 24318 槽（约 −73%）。原因是固定指数切法把近裁面
附近切成很多极薄的片（0.10–0.14m、0.14–0.18m…），灯团横跨多个薄片就被复制多份；自适应把远处
空区合并成少数大片、把分辨率压到灯团所在的少数深度，重复副本因此大减。

**结论 2：查询成本跟着列表量走，但须与“可见几何在哪”一起看。**
近面灯团固定切分每像素均值 37.9 盏、自适应 33.8 盏；但在**紧预算 C=8** 下自适应反而从 27.2 降到
21.8（固定 27.2 → 自适应 21.8），因为固定切法在近裁面制造了过多超容量薄片、把大量灯推进溢出/全局表。
侧向环绕场景两者差距很小（0.65 vs 2.52 每像素）——当相机主要看向空街、几何贴着某一深度时，
自适应的优势被“几乎没有近处几何可浪费”抵消。

**结论 3：没有一种切法全面胜出。**
均匀灯群下自适应省索引（14046→9639），但每像素均值略高（23.9→27.9），因为等质量分位会在若干
深度片集中更多瓦片；近面灯团下自适应在索引与紧预算查询量上都更好。取舍取决于负载的深度直方图形状。

> 诚实边界：结果取决于灯群与预算，并非“自适应恒省”。例如仓库默认的 128 盏夜市灯、C=24 时，
> 界面「深度分区方案对照」会实测到自适应索引反而更高（约 25711 vs 固定 17478 槽），因为
> 夜市的近处灯既密又连续占据大片近深区间，等质量分位会把近区拆成许多仍需大量复制的片。
> 同一卡片会用当前灯群实时复算这一行，读者应以其为准，而不是把本节的 96 灯数值当成恒真。

## 4. 最先超出容量的簇

`firstOverCapacity()` 按簇 id 顺序找出**第一个**原始候选数超过容量的簇（不是全局最大，而是“最先
撞线”的那个，符合“用相同索引预算跑、标出最先超容量”的要求）。

| 场景 | 固定：最先超容量簇 | 自适应：最先超容量簇 |
| --- | --- | --- |
| 均匀灯群 | tile(1,0) s12，17/16，4.00–5.44m | tile(0,0) s0，24/16，0.10–10.06m |
| 近面灯团 | tile(0,0) s0，67/16，0.10–0.14m | tile(0,0) s0，77/16，0.10–10.06m |
| 近面灯团 · 紧 C=8 | tile(0,0) s0，67/8，0.10–0.14m | tile(0,0) s0，77/8，0.10–10.06m |
| 侧向环绕 | tile(14,0) s16，21/16，13.68–18.60m | tile(15,4) s21，18/16，12.68–15.06m |

注意固定切分的第一片 `0.10–0.14m` 薄到几乎不装任何可见几何，却常是“最先超容量”的簇——这正是固定
指数切法对近面密灯不友好的直接证据。自适应方案的第一片覆盖近处可见区间（如 0.10–10.06m），容量压力
更早暴露在**真正有几何**的深度上，而不是被一个空薄片的索引记账。

所有超容量簇都由「混合策略」完整容纳（宽灯进独立全局表、其余进有界主表+溢出），**不截断**。

## 5. 空区与密集局部灯光的列表长度

`perSliceSummary()` 给出每个深度片内所有瓦片的列表长度均值/峰值、空瓦片数、超容量瓦片数
（完整 24 片表见 `artifacts/cluster-experiment.md` 的「每深度片列表长度」）。

- **空区**：固定切分在近裁面前几片（0.10–0.63m）均值=0、空瓦片=全部——片是“满的”但没有任何灯/几何，
  这些片的存在纯属稳定划分的代价；自适应把空区并成少数大片，减少空转片。
- **密集局部灯光**：近面灯团下，固定切分在 0.10–0.14m 的薄片峰值可达 60+ 盏并反复超容量，而真正的
  灯团其实横跨若干片；自适应把这些深度合并后，超容量瓦片数从 2379 降到 1394。

**查询成本**（每像素实际循环灯数，来自 `renderImage` 的 `iterMap`）随列表长度线性变化，两者在
`verify.mjs` 中都被断言为“零漏光 + 与全灯参考一致”。我们没有用“少循环=少灯”换数字：漏光计数为 0。

## 6. 对照实验：真的截断列表会怎样（被禁止的捷径）

为让“0 漏光”的结论有意义，`measureTruncationError()` 故意只保留每簇主表、丢掉溢出与全局表，
量出这种“截断省负载”捷径的代价：

| 场景 | 分区 | PSNR | 最大差 | 漏光（覆盖缺失） |
| --- | --- | --- | --- | --- |
| 均匀灯群 | 固定 | 14.24 dB | 大 | 292852 |
| 均匀灯群 | 自适应 | 7.90 dB | 大 | 529607 |
| 近面灯团 | 固定 | 15.05 dB | 大 | 508121 |
| 近面灯团 | 自适应 | 14.79 dB | 大 | 533090 |

截断会让 PSNR 从 ∞ 掉到 ~8–15 dB、漏光几十万次。**这正是本实验拒绝走的路径**，也证明第 3 节里
“零误差 + 更少索引/更少循环”的结论不是靠漏灯换来的。`verify.mjs` 有一条硬检查要求该对照确实
“漏光>0 且 PSNR<40”，否则视为实验失真。

## 7. 界限（可复算的边界，而非口号）

`findMinIndexBudget()` 从 0 二分出「仍能发布完整、零漏光帧」所必需的最小总索引预算：

| 场景 | 固定最小索引预算 | 自适应最小索引预算 |
| --- | --- | --- |
| 均匀灯群 | 14046 | 9639 |
| 近面灯团 | 88732 | 24318 |
| 均匀灯群 · 紧 C=8 | 16215 | 31122 |
| 近面灯团 · 紧 C=8 | 134892 | 47799 |
| 侧向环绕 | 7785 | 8039 |

这些就是“在给定容量 C 与全局预算 G 下，某分区要完整发布至少要多少索引槽”的下界；低于它内核
**不会**截断任何簇，而是保留上一个完整帧、把相关簇标为待算（`pending`），界面用斜纹显示。

**可陈述的界限**：

- 固定指数切分在**深度分布接近对数均匀**（均匀灯群）时索引最省；一旦出现**近面密灯**
  （近面灯团），固定切法的薄片复制会把索引量推到自适应方案的 ~3–4 倍。
- 自适应在**近面密灯 + 远处空区**下索引与紧预算查询量都更优，但需要一次可见深度采样
  （本实验 ~4384 个命中点，确定性），且边界随相机变化。
- 两种方案都**不可能**在容量 C 下“零成本”容纳任意密集灯团：当某深度片内真实同屏灯数持续 > C，
  必须动用全局表或溢出表（本仓库默认混合策略），否则只会变成“待算”或“截断导致误差”。
  这就是列表量的硬界限——它由最密深度片的灯数决定，不由切法消除。

## 8. 生产接点与图形入口（不只是架构文字）

分簇灯光是**真实接进渲染管线**的，不是文档占位：

- **着色器接点**：`src/app/shaders.js` 的 `SCENE_FRAG` 读 `uHeaderTex` / `uIndexTex` / `uLightTex` 与
  `uBoundaries[41]`，逐像素取片→取簇→循环该簇局部灯 + 全局表灯。固定/自适应共用此着色器。
- **上传接点**：`src/app/webglRenderer.js` 的 `_uploadFrame()` 把 `headerData`/`indexData`/灯表与
  `cfg.boundaries` 整体上传；帧版本变化才重传，避免新旧分区混用。
- **图形入口**：`npm start` → 浏览器打开终端打印的 `http://localhost:5180/`。
  - 视口「光栅调试」下拉切换：正常光照 / 簇内灯数热图 / 深度层分带 / 簇 ID 伪彩 / 线性深度映射。
  - 右栏「深度分区方案」下拉实时切 fixed / adaptive，视口与检查器同步重算。
  - 「深度分区方案对照」卡片：一次点击同时渲染**固定**与**自适应**两幅分簇光照图、两者的差异图，
    并列出两方案的 PSNR / 漏光 / 每像素灯数 / 索引槽 / 最先超容量簇，以及每深度片列表长度柱状图。
  - 点画面取簇 → 「簇检查器」显示该簇主表/溢出/全局灯源与逐灯贡献，可「关/独」核对亮斑来源。
- **命令行仅作辅助**：`npm run verify`（正确性 + 边界）、`npm run experiment`（复算本文数字）、
  `npm run shot`（无头浏览器驱动上面的图形入口并截图）。文档与操作以图形入口为准。

## 9. 如何复算

```bash
npm install            # 首次
npm run verify         # 深度一致性、零漏光、固定/自适应边界、截断对照、预算状态机
npm run experiment     # 复算 artifacts/cluster-experiment.json 与 .md（本文所有数字）
npm start              # 图形入口；浏览器里切换分区、运行「深度分区方案对照」
```

`npm run experiment` 若任何场景漏光或违反帧不变量会**非零退出**，因此上面表格的数字不会被一次
“悄悄漏灯”的运行替换掉。
